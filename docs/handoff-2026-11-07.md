## 2. ObjectBox mode (`TFE_CODE_INDEX=objectbox`)

The role tree can now live in the engine's ObjectBox store instead of
`.tfe-code/project.json`.

Build: `CMakeLists.txt` forces `TEXTFOUNDRY_ENGINE_BUILD_OBJECTBOX_STORE=ON` and
links `textfoundry_core` and `textfoundry_objectbox_store` through
`$<LINK_GROUP:RESCAN,…>` — without the link group `Engine::FullInit()` is
undefined because static-library order puts the store before the core that needs
it.

Mapping, one `Block` per role, in `native/objectbox_store.cc`:

| Role | Block |
| --- | --- |
| id | block id |
| text | template |
| SHA-256, `literal`, source ranges, `empty` flag | JSON in `description` |
| file → root role + params | one `Meta` block per file, id `file:<path>` |

Two consequences worth knowing:

- **Versions.** The engine `Version` is `major.minor`, so the content hash the
  `apply` contract needs is kept in `description`. A new role publishes `1.0`;
  every edit publishes the next minor, so history accumulates for free. Nothing
  exposes that history through the CLI yet.
- **Empty roles.** `Block::publish` rejects an empty template, but an empty
  `__init__.py` is valid code. The adapter stores a placeholder plus
  `"empty": true` and decodes by the flag, so real text can never be confused
  with the placeholder.

`ObjectBoxRoleStore::Save` publishes the whole batch inside one
`obx::Transaction`. A failure part-way leaves the store unchanged — tested by
`test_objectbox_store_core`, which publishes one role, fails on the next, and
asserts the database is untouched.

**Authority in this mode, stated precisely.** The source files are rendered
output and the database holds the role tree, but the mirror still decides when
the two disagree:

- a workspace containing only `.tfe-code/db` is valid: `LoadForImport` falls back
  to the store when `project.json` is absent;
- when `project.json` is present the mirror is loaded first, and the stored tree
  is served only if its serialised hash equals `state.project_hash`;
- on disagreement the **mirror wins** and its content is republished into the
  database, so a stale index can never be presented as the current tree.

That means the database is the working index, not the final arbiter: the mirror
is what a disagreement resolves towards. Earlier wording calling the database
outright authoritative was wrong.

`apply --check` publishes to the database only **after** the check passes. This
order matters in a database-only workspace: there is no mirror to rebuild from,
so publishing first would leave rejected roles in the store while the files
rolled back. `test_objectbox_check_rollback_core` pins that down.

`tfe-code render` returns the tree; `tfe-code render --write` materialises it and
returns only the list of written paths. (It used to echo every file's contents —
165 KB instead of 4 KB on the consumer project.)

**Recovery is weaker here and the documentation says so.** The crash journal
snapshots files, and a binary store cannot be byte-snapshotted. After an
interruption the index is rebuilt from the mirror, not restored. Do not describe
this as transactional recovery of the database.

## 3. Engine extension

`EngineConfig::defer_init` was added (`tf/engine.h`, `tf/engine.cc`). When true,
both constructors skip `FullInit()`, so a consumer can supply its own
repositories. This is required because ObjectBox allows one open store per path
per process, and the adapter must own that store to wrap a batch in a
transaction. Keep ObjectBox types out of `engine.h` and out of
`native/workspace.h`; only `native/objectbox_store.{h,cc}` may include them.

## 4. Engine logging

`native/main.cc` sets the engine log level to `Off` by default. The engine logs
`Block not found` as an **error** for every role's first publish, and the
experiment agent merges stderr into command output, so leaving it on inflates
every measured attempt. `TFE_CODE_LOG=error|info|debug` restores detail. If you
change the default back, every cost measurement becomes incomparable.

## 5. Experiment harness

Two harnesses exist, both run through one driver:

```text
harness/tabletop/   task: cache-aware LLM cost accounting (53-line file)
harness/span/       task: single-line span names (457-line file)
harness/tabletop/setup.sh   builds both arms for a given harness directory
scripts/tabletop_paired_trial.py
```

Arms:

- `files` — the project as it exists, edited with shell tools;
- `db` — `src/` empty, role tree only in `.tfe-code/db`, edited through
  `tfe-code`, materialised with `render --write`.

Invocation:

```bash
./harness/tabletop/setup.sh /tmp/arms /abs/path/to/harness/span
TFE_TRIAL_HARNESS=$PWD/harness/span python3 scripts/tabletop_paired_trial.py \
  --out /tmp/run --go-ahead --budget 20.0 --attempt-budget 5.0 --reps 3
```

`setup.sh` needs no model. The driver requires `--go-ahead` and a budget, and
reads the API key from `../TextFoundryEngine/.dt.key`. It refuses to reuse an
existing `--out`.

**Grading replays the artefact into a pristine template** and runs the
independent verifier plus the project suite there, so weakening a test inside an
attempt cannot help. Both arms start from an identical `verify.py` that is RED
before the change.

Cost: the provider reports tokens but no price, so every attempt is marked
`cost_source: computed_from_tariff` at **33 RUB / 1M input and 133 RUB / 1M
output** (`role_contracts/tariff_cost.py`). Cached input is not billed
separately. An independent recount from the raw events reproduces the totals
exactly; keep doing that when you change anything in the accounting path.

## 6. Sandbox traps (these cost about 25 RUB to discover)

The agent runs under `bwrap` in `experiments/code-fragments-spike/api_agent.py`.
Four things break silently and each one wastes an entire run:

1. **`$HOME` is masked** with a tmpfs, so a project `.venv` under `$HOME` is
   invisible. Pass `--expose PATH`; the code recreates the ancestor directories
   with `--dir`, because bwrap will not bind into a path whose parents are
   missing.
2. **The interpreter is a symlink chain.** `.venv/bin/python` links into
   `~/.local/share/uv/python/cpython-3.13-…`, and an intermediate symlink points
   at `cpython-3.13.14-…`. Expose the whole `uv/python` directory, not the
   resolved version.
3. **`--clearenv` drops everything.** Setting a variable on the parent process is
   not enough; pass `--env KEY=VALUE`. Note bwrap's `--setenv` takes **two**
   arguments, so the key and value must be split.
4. **The package is installed editable against the original project.** A `.pth`
   in the venv points at the real `src/`, so any `pytest`/`import` without
   `PYTHONPATH=<arm>/src` silently tests the untouched original. This bit the
   grading path too: the verifier imported the original and reported correct
   edits as failures. Always set `PYTHONPATH` for both the suite and the
   verifier.

A fifth, purely my own: after adding a repetition loop, check the indentation of
everything following `shutil.copytree`. An off-by-one dedent ran only the last
arm of each round and produced three empty run directories.

Symptom to recognise: an agent that spends 6–14 steps on `strings`, `objdump`,
`find /` or `ls /home/...` is fighting the sandbox, not the task. Stop and check
the four items above before reading anything into the numbers.

differences are cost only.

Limits section says **"The template is planted, not imported"**, so that fixture
does not exist in real code. `holdout` independently found that savings did not
transfer to new tasks.

## 8. CLI defects found and fixed

Discovered by watching the agent, each worth real money:

- `tfe-code help` and `--help` returned exit 2, so an agent concluded the tool
  was broken and started dissecting the binary. Now exit 0.
- `apply --help` did not exist; the agent guessed the JSON shape, sent an array
  with `expect_version`, and received `Could not cast to object!`. It then spent
  six steps on `strings ./tfe-code`. Now `apply --help` prints the schema and a
  parse failure repeats it.
- `render --write` echoed every file's contents. Now it returns only the written
  paths.

The durable lesson: an error message that does not name the expected shape turns
into binary reverse-engineering, and that costs more than the feature.

## 9. Known limits

- Database-mode crash recovery rebuilds the index; it does not restore it.
- ObjectBox history (`major.minor`) exists but no command exposes it.
- Each harness's `verify.py` is written by hand. A wrong expectation is
  indistinguishable from a real failure until a reference implementation is run
  through it — doing that caught two bad assertions this session. Always do it
  before a paid series.
- Two tasks, one model, one provider. Nothing here is a repository-wide claim.
- The consumer project has two pre-existing test failures
  (`test_service_session_scope`, `test_session_manager`) and one file with a
  collection error (`test_sessions_controller.py`); the gate deselects all three.
  If they are fixed upstream, update the gate in `setup.sh` and in `grade()`.

## 10. Suggested next steps

1. **Decide what the product is.** The cost hypothesis has now failed on real
   handwritten code three times (`holdout`, Task A, Task B). Either target
   generated or cross-language artefacts, where `import` genuinely cannot
   deduplicate, or stop selling cost and sell determinism, verifiable receipts
   and rollback instead.
2. If the cross-language case matters, the consumer project cannot test it: it is
   single-language Python with no schema or QML mirrors. A fixture with a real
   projection is required — and the competitor there is a **code generator**, not
   `cat`.
3. Expose the ObjectBox version history. It already exists and is the one
   capability the file mode cannot offer.
4. Before any further paid run: run a reference implementation through the
   verifier and the project suite, and recount the cost from raw events.

## 12. Risks raised in `handoff-2026-11-07-economics.md` — resolved

A later session flagged two open correctness risks in the ObjectBox mode. Both
were real; both are now closed.

**Risk: a failing `apply --check` could leave a published change in the store.**
Reproduced, not merely suspected. `Commit` published to ObjectBox *before*
running the check, and the rollback restores only files. In a database-only
workspace there is no mirror to rebuild from, so a rejected batch stayed in the
store while the sources rolled back. `Commit` now publishes **after** the check
passes, and `tests/native/test_objectbox_check_rollback_core.cc` fails with
`a rejected batch left its edit published in the database` on the old order and
passes on the new one.

**Risk: the documentation overstated the database's authority.** `LoadForImport`
reads `project.json` first and only falls back to the store when the mirror is
absent; on a hash mismatch the mirror wins and is republished into the store. The
earlier wording "the database is authoritative" was wrong and is corrected in
§2, in `docs/architecture.md` and in `AGENTS.md`.

The third item in that list — that per-block `major.minor` versions do not by
themselves prove project-wide history or rollback — stands and is a real limit,
not a defect: no command exposes history, and nothing claims it.
