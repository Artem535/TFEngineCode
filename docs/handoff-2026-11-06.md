## 2. Критически важно: состояние Git

Практически вся разработка находится в **uncommitted working tree**. Большинство native C++ файлов и native-тестов являются untracked.

Следующий исполнитель не должен без отдельного явного разрешения пользователя выполнять:

```bash
git reset
git checkout -- ...
git clean
git stash
```

Также не выполнять без явного запроса:

- commit;
- push;
- branch/switch;
- merge/rebase;
- создание MR/PR;
- удаление untracked-файлов;
- очистку `.superpowers/`.

Эти действия могут удалить основной результат работы. `HEAD` не отражает текущую реализацию, поэтому review нужно проводить по текущим файлам, а не только по `git diff HEAD`.

## 3. Назначение проекта

TFEngine Code предоставляет интерфейс для чтения и редактирования Python-кода как дерева именованных ролей. Рендеринг выполняется через C++ TextFoundryEngine.

Основная модель:

- файл разбивается на file/class/function/method/nested-function роли;
- родитель ссылается на дочернюю роль через `{{role.id}}`;
- indentation принадлежит родителю;
- текст роли хранится dedented;
- агент читает только необходимые роли;
- связанные изменения отправляются одним batch;
- обычные исходные Python-файлы остаются authoritative;
- `.tfe-code/` содержит производный индекс и состояние согласованности.

Проект остаётся экспериментальным. Это пока не реализация Engine/ObjectBox publication или полноценной version history.

## 4. Два раздельных workflow

### Native imported workspace

Основной новый workflow, реализованный на **C++23**.

Использует:

```text
.tfe-code/project.json
.tfe-code/state.json
.tfe-code/lock
.tfe-code/transaction.json  # только во время незавершённой транзакции
```

Предназначен для импорта и редактирования существующего Python-проекта на месте.

### Legacy explicit templates

Старый Python CLI для явных `#@`-документов.

Использует:

```text
.roles/store.json
out/
```

Поддерживает explicit templates, `put`, `replace`, `file` mappings и legacy `#@ apply`. Этот режим намеренно сохранён отдельно. Новую native-функциональность в него не переносить.

Python в текущей разработке нужен для:

- legacy CLI;
- integration tests;
- offline rehearsal.

Вся новая производственная native-логика пишется на C++.

## 5. Реализованные native-команды

```text
tfe-code ignore
tfe-code import PATH...
tfe-code outline [FILE_OR_ROLE] [--depth N]
tfe-code tree FILE_OR_ROLE
tfe-code show ROLE... [--json]
tfe-code search QUERY... [--prefix PREFIX]
tfe-code who [PREFIX.] NAME...
tfe-code apply [--check COMMAND] < edits.json
tfe-code render
tfe-code sync
tfe-code check COMMAND
```

### `ignore`

Создаёт `.tfe-codeignore` с правилами по умолчанию и не перезаписывает существующий файл.

### `import`

Поддерживает:

- отдельные `.py` файлы;
- директории;
- `import .` для всего проекта;
- sorted/deduplicated expansion;
- byte-exact проверку через реальный renderer.

### `outline`

Показывает иерархию, размер роли и доступные source ranges.

Пример метаданных:

```text
sample.first (2 lines; source 1-2)
```

### `tree`

Возвращает полное поддерево с версиями. Его формат не изменялся при добавлении source ranges.

### `show`

Plain text добавляет доступный диапазон:

```text
#@ sample.first [version: ...] [lines: 1-2]
```

JSON содержит:

```json
{
  "source_start_line": 1,
  "source_end_line": 2
}
```

### `search` / `who`

Выполняют case-sensitive literal matching по role ID и тексту. Поддерживают prefix filtering и возвращают полные роли с версиями.

### `apply`

Принимает JSON batch:

```json
{
  "edits": [
    {
      "role": "package.module.function",
      "expected_version": "VERSION_FROM_SHOW",
      "old": "return 1",
      "new": "return 2"
    }
  ]
}
```

Правила:

- `old` обязан быть nonempty;
- `old` должен совпасть ровно один раз в тексте роли;
- `expected_version` должен соответствовать текущей версии;
- дубликаты роли в одном batch отклоняются;
- связанные роли изменяются одной транзакцией;
- `--check COMMAND` запускает реальную проверку в consumer workspace;
- при handled failure выполняется rollback sources/project/state.

### `sync`

Обрабатывает:

- внешние изменения managed source;
- удаления managed-файлов;
- exact rename по SHA-256 содержимого;
- обновление source ranges;
- deterministic `changed`;
- повторный clean sync.

Не выполняет:

- автоматический импорт unrelated new files;
- inference edited rename;
- automatic conflict merge;
- выбор при ambiguous duplicate-content rename.

## 6. Python import

Основная реализация:

```text
native/python_import.cc
native/python_import.h
```

Используется tree-sitter Python grammar на pinned commit.

Поддерживаются:

- files;
- classes;
- functions;
- methods;
- nested functions;
- decorators;
- CRLF;
- Unicode;
- empty source;
- missing final newline;
- byte-exact rendering.

Candidate отклоняется при:

- syntax error;
- unsafe path;
- role collision;
- потере исходных байтов.

Двойные скобки в обычных Python string literals, например `"{{not.a_role}}"`, не должны становиться причиной ложного role lookup во время refresh source ranges. Для этого есть regression-тест.

## 7. Source line ranges

В `native/project.h` у `Node` есть trailing fields:

```cpp
size_t source_start_line = 0;
size_t source_end_line = 0;
```

Семантика:

- 1-based;
- inclusive;
- tree-sitter exclusive end преобразуется в inclusive line;
- диапазоны обновляются на `import`, `apply`, `sync`;
- refresh выполняется из rendered candidate bytes;
- ranges копируются только для совпадающих role IDs;
- unmatched role получает `0/0`, а не stale coordinates;
- empty и legacy roles также используют `0/0`;
- ranges являются navigation metadata, а не identity, version или history.

Для чтения legacy Project JSON используется `rfl::DefaultIfMissing`, потому что обычных C++ member defaults недостаточно для reflect-cpp. State и apply JSON остаются строгими.

## 8. Crash recovery

Последний завершённый крупный срез.

Основные места:

```text
native/workspace.cc
native/workspace.h
tests/native/test_workspace.cc
tests/test_cli.py
```

### Модель

Перед первым managed write `Workspace::Commit()` создаёт:

```text
.tfe-code/transaction.json
```

Journal содержит:

- `schema`;
- `entries`;
- root-relative `path`;
- `original` с исходными байтами;
- explicit JSON `null`, если файл раньше отсутствовал.

### Порядок транзакции

1. Проверяются concurrent source changes.
2. Candidate рендерится и полностью парсится.
3. Сохраняются original bytes/absence всех touched files.
4. Атомарно записывается journal.
5. Записываются changed sources.
6. Записываются project и state.
7. При наличии запускается check и обновляется receipt.
8. Journal удаляется только после успешного завершения.

### Recovery

При наличии journal следующая валидная native-команда:

1. Захватывает `.tfe-code/lock`.
2. Повторно проверяет наличие journal.
3. Полностью валидирует journal до изменения файлов.
4. Восстанавливает originals или удаляет файлы, которые раньше отсутствовали.
5. Удаляет journal только после полного восстановления.

Recovery идемпотентен. Если recovery прервался или restore завершился ошибкой, journal остаётся для следующей попытки.

Writer paths вызывают recovery до захвата основного lock. Под уже захваченным lock используется `LoadConsistent(false)`, чтобы избежать nested locking.

### Валидация journal

Используются:

```cpp
rfl::NoOptionals
rfl::NoExtraFields
```

Дополнительно проверяются:

- schema;
- обязательные project/state entries;
- nonempty/complete transaction;
- canonical-path duplicates;
- разрешённые пути;
- отсутствие изменений до завершения полной валидации.

Malformed journal должен остаться на месте и не изменить managed files.

### Test crash point

Для реальных process-crash тестов реализована переменная:

```text
TFE_CODE_TEST_CRASH_AFTER=/absolute/path/to/file
```

После соответствующего managed `AtomicWrite()` процесс вызывает `_exit(90)`.

Проверены падения после записи:

- первого source;
- `.tfe-code/project.json`;
- `.tfe-code/state.json`.

Есть отдельный CLI end-to-end test восстановления и повторного apply.

### Границы гарантии

Реализовано восстановление после **process interruption**. Не заявляется:

- OS crash/power-loss durability;
- fsync-based durability;
- rollback внешних side effects check command;
- rollback unmanaged files;
- автоматическое разрешение ручных изменений, сделанных после crash.

## 13. Отложенные Minor и известные ограничения

### Crash recovery

Отложено:

- расширить crash matrix на first import;
- проверить падение после второго и последующего source;
- отдельно проверить receipt rewrite после check;
- проверить прерывание самого recovery;
- уточнить wording для прерывания после удаления journal, но до возврата CLI результата.

Текущая фраза skill «interruption saves no passing receipt» слишком абсолютна для случая, когда journal уже удалён, а CLI ещё не вернул результат. Это документационный Minor, не дефект recovery.

### Source ranges

Можно усилить boundary tests чтения legacy Project JSON через реальные Workspace/renderer entry points. Текущий compatibility test проверяет standalone `Node` с `DefaultIfMissing`.

### Sync/portability

Rename/rename ambiguity реализованы и проверены в POSIX-среде. Case-insensitive filesystems и кроссплатформенное поведение не специфицированы.

### Общие ограничения

- Нет automatic conflict merge.
- Нет runtime sandbox для check commands.
- Нет publication history.
- Нет Engine/ObjectBox persistence в TFEngine Code.
- Legacy Python CLI не имеет native rollback/recovery guarantees.
- Native `put`, `replace`, `file` и legacy `#@ apply` намеренно не дублировались: native workflow использует JSON apply. Менять это решение только при новом требовании.

## 16. Рекомендуемый следующий шаг

### Предпочтительно: отдельный design slice для ObjectBox

Пользователь ранее отдельно спрашивал о переходе к ObjectBox, поскольку он используется движком. Сейчас в `CMakeLists.txt` явно установлено:

```cmake
set(TEXTFOUNDRY_ENGINE_BUILD_OBJECTBOX_STORE OFF CACHE BOOL "" FORCE)
```

ObjectBox для TFEngine Code не требуется и не используется.

Перед реализацией нужно исследовать API движка и согласовать:

- что именно должно храниться в ObjectBox: roles, files, versions, state, receipts;
- является ли ObjectBox authoritative или заменяет только derived JSON index;
- как сохранить source-authoritative semantics;
- миграцию существующих `.tfe-code` workspaces;
- transaction/recovery semantics;
- compatibility с legacy renderer;
- версии и publication history;
- зависимости и сборку consumer project;
- rollback/migration failure behavior.

Не начинать с механической замены JSON на ObjectBox. Сначала подготовить небольшой design plan и проверить реальный API внешнего движка.

### Альтернатива: небольшой hardening slice

Если ObjectBox пока не приоритетен, закрыть deferred crash recovery tests и documentation wording. Это меньший самостоятельный срез.
